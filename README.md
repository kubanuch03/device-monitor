# Device Monitor

Сервис проверяет доступность сетевых устройств по нескольким площадкам и даёт
открыть их веб-интерфейс в один клик. Камеры, домофоны, шлагбаумы, коммутаторы,
серверы — всё, у чего есть IP и открытый порт.

Задача, из которой он вырос: устройства на объектах сидят на DHCP без
резерваций, адреса протухают, и в момент, когда что-то не открывается, непонятно
— адрес сменился, устройство выключено или пропала связь с площадкой целиком.

К парковке и любой другой прикладной системе сервис не привязан. Стек:
**FastAPI + SQLAlchemy (SQLite) + Pydantic**, фронтенд — статические файлы.
API версионирован (`/api/v1`), с автодокументацией на `/docs`.

## Быстрый старт

```bash
cp data/devices.example.json data/devices.json   # или начните с пустого списка
docker compose up -d
```

Панель — <http://127.0.0.1:8890>. Навигация в три уровня:

```
Точки  →  Категории точки  →  Устройства
```

Главный экран — список точек. Заходите в точку — видите её категории (камеры,
домофоны, шлагбаумы, терминалы). Заходите в категорию — видите устройства.
Точка и категория заводятся кнопками «Новая точка» и «Новая категория»,
устройство — «Добавить устройство сюда». У карточки есть «Дублировать» — удобно,
когда на объекте четыре одинаковых камеры и меняется только адрес.

Текущий экран записан в адресе страницы, поэтому перезагрузка и ссылка в новой
вкладке возвращают ровно туда, где вы были. Файл править руками не обязательно.

Без докера:

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
DM_PASSWORD=<пароль> python3 monitor.py
```

API-документация (OpenAPI/Swagger) — на `/docs`. Тесты: `pip install -r
requirements-dev.txt && pytest`.

## Как проверяется доступность

TCP-коннектом на каждый указанный порт. Устройство считается живым, если открыт
хотя бы один порт; в карточке видно, какой именно открыт, а какой нет — у камеры
Dahua это обычно `80` (веб), `554` (RTSP) и `37777` (частный протокол), и
ситуация «веб отвечает, RTSP нет» диагностируется сразу.

Проверка идёт **с сервера, а не из браузера**. Браузерная проба умеет только
HTTP, ничего не помнит между открытиями страницы, не работает при закрытой
вкладке и зависит от политик браузера: страница, открытая как `file://`,
считается защищённым контекстом, и тогда запросы к `http://` режутся как mixed
content — все устройства выглядят мёртвыми, хотя они живы.

Поле «в этом состоянии N» сбрасывается только при смене статуса и отвечает на
главный вопрос дежурного: это упало только что или лежит со вчера.

## Настройки

Всё через переменные окружения (см. `docker-compose.yml`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `DM_HOST` | `127.0.0.1` | Адрес, на котором слушает панель |
| `DM_PORT` | `8890` | Порт панели |
| `DM_POLL_INTERVAL` | `20` | Секунд между кругами опроса |
| `DM_PROBE_TIMEOUT` | `3` | Секунд ждать TCP-коннекта |
| `DM_DATA_DIR` | `data/` | Каталог базы |
| `DM_PASSWORD` | — | Пароль панели; пусто = открыта, но учётки хранить нельзя |
| `DM_HISTORY_DAYS` | `90` | Сколько хранить историю состояний |
| `DM_INSPECT_TTL` | `900` | Как часто переспрашивать сведения у железа, сек |
| `DM_WORKERS` | `32` | Одновременных проверок |

### Два важных пункта

**`network_mode: host` обязателен, а не для удобства.** Проверка идёт с сервера,
поэтому контейнер должен видеть ровно те же сети, что и хост. VPN-маршруты
(WireGuard, OpenVPN) живут на хосте и в обычную bridge-сеть Docker не попадают —
без host-режима сервис будет уверенно докладывать, что вся площадка мертва.

**`user:` в compose должен совпадать с владельцем каталога `data`.** Каталог
монтируется с хоста, и процесс в контейнере пишет в него от своего uid. По
умолчанию стоит `1000:1000` — обычный первый пользователь в Linux. Если у вас
другой (`id -u`, `id -g`), задайте `DM_UID` и `DM_GID`, иначе сохранение списка
упадёт с ошибкой прав — сервис об этом скажет прямо в интерфейсе.

**Авторизации у сервиса нет.** Поэтому по умолчанию он слушает `127.0.0.1` и
доступен только с этой машины. Ставьте `DM_HOST=0.0.0.0`, только если сознательно
открываете панель коллегам по локальной сети.

## Вход и учётные данные

Вход в панель — по логину и паролю (учётка хранится в БД, пароль — необратимым
pbkdf2-хешем). **При первом запуске создаётся дефолтная учётка `admin` / пароль
из `config.DEFAULT_PASSWORD`.** Репозиторий публичный, поэтому дефолтный пароль
секретом не является — смените его после первого входа через кнопку «Аккаунт»,
либо задайте свой до первого запуска через `DM_DEFAULT_USERNAME` /
`DM_DEFAULT_PASSWORD` в `docker-compose.yml`.

Пароль устройства наружу не отдаётся никогда — ни в API, ни в экспорте: клиент
видит только признак «пароль задан». В файле базы он лежит закодированным (не
зашифрованным — честно: ключ пришлось бы держать рядом, и защита была бы
показной; реальная защита — права `600` на файл и пароль на панель). Учётки
нужны, чтобы сервис сам спрашивал у железа модель, серийник и прошивку — Dahua
через `magicBox.cgi`, Hikvision через `ISAPI`. Производитель и модель Hikvision
видны и без пароля, по ответу устройства на запрос без авторизации.

Секрет по сети идёт в открытом виде, а cookie сессии без флага Secure, поэтому
**наружу панель можно открывать только за HTTPS-прокси**. По умолчанию она
слушает `127.0.0.1`.

## Хранение

Данные — в `data/monitor.db` (SQLite через SQLAlchemy ORM): устройства, точки,
категории, история состояний. При первом запуске старый `data/devices.json`,
если он есть, переносится автоматически (сохраняется как `devices.json.migrated`).
Схема совместима — базы прежних версий читаются как есть. База в `.gitignore`.

История пишется по сменам состояния, а не по каждой проверке, и хранится
`DM_HISTORY_DAYS` дней (по умолчанию 90). Отсюда берутся аптайм в процентах и
число падений в карточке устройства.

```json
{
  "site": "ТЦ Ала-Арча",
  "category": "Камеры",
  "name": "Камера ANPR, въезд 1",
  "host": "10.30.205.24",
  "ports": [80, 554, 37777],
  "scheme": "http",
  "web_port": null,
  "path": "/",
  "note": "Dahua ITC413"
}
```

`site` ссылается на точку по имени. Точки лежат в том же файле отдельным
списком, поэтому пустая точка существует сама по себе — можно завести её заранее
и наполнять потом. Переименование идёт каскадом: устройства переезжают вместе с
точкой. Удалить точку с устройствами нельзя — сначала перенесите или удалите их.

`category` — категория внутри точки. Категории хранятся отдельным списком и
привязаны к своей точке, поэтому существуют и пустыми: можно завести структуру
заранее и наполнять потом. Переименование идёт каскадом, удалить непустую нельзя.
Устройства, которым категорию не проставили, показываются отдельной плиткой
«Без категории» — и только когда они есть.

Переименование точки тянет за собой и её категории; удаление точки убирает их
вместе с ней, чтобы в файле не оставалось невидимого мусора.

`web_port` и `path` нужны, когда интерфейс висит не в корне и не на стандартном
порту. Вписывать их по отдельности не обязательно: в поле «Адрес» можно вставить
ссылку целиком, вида `http://10.30.205.243:8833/admin/`, — схема, порт и путь
разберутся сами.

Файлы первой версии (без списка точек) открываются без миграции: точки
восстанавливаются из устройств.

## Устройство кода

```
monitor.py                 точка входа: сборка и запуск
device_monitor/
  config.py                настройки, единственный читатель окружения
  security.py              пароли, сессии
  domain/                  модели, валидация — не знают про SQL и HTTP
  storage/                 base.py (контракт) + sqlite.py (реализация)
  vendors/                 registry + dahua.py + hikvision.py — по файлу на вендора
  probing/                 tcp.py (проверка) + monitor.py (фоновый цикл)
  web/                     api.py (логика) + fastapi_app.py (роуты /api/v1) + schemas.py (Pydantic)
  storage/                 base.py (контракт) + sqlalchemy_store.py
tests/                     pytest — API и хранилище
```

Границы проведены так, чтобы самое вероятное расширение стоило нового файла, а
не правки существующих: новый вендор — файл в `vendors/`, другая БД — файл в
`storage/`, другой транспорт (FastAPI) — замена `web/server.py` без единой
правки логики в `web/api.py`.

## Один монитор на объект

Проверка идёт с той машины, где запущен сервис, поэтому монитор видит только те
сети, до которых у этой машины есть маршрут. Устройства объекта, до которого нет
ни прямого маршрута, ни VPN, ни туннеля, будут вечно показываться offline — это
не поломка, а честный ответ «отсюда не достучаться».

Отсюда модель: **по монитору на объект**, запущенному внутри его сети
(`docker compose up` на сервере объекта — `network_mode: host` даст ему ту же
сеть, что видит сам сервер). Один центральный монитор на все объекты возможен,
но потребует туннеля/VPN до каждой площадки.

## Когда переходить на Postgres

SQLite здесь не временное решение, а осознанное: одному сервису с десятками
записей в минуту его хватает с запасом, а стоит он ноль зависимостей и ноль
обслуживания. Переходить на Postgres стоит, только когда появляется что-то из
этого: мониторов несколько и они пишут в одну базу; к данным нужен сетевой
доступ из других инструментов; история разрослась до сотен тысяч событий с
тяжёлой аналитикой; нужны роли и права на уровне БД. Благодаря слою
`storage/` переход стоит одного нового файла `storage/postgres.py` — опрос,
вендоры и веб не меняются.

## Как добавить поддержку нового вендора

Один файл в `device_monitor/vendors/` с классом-наследником `VendorDriver`
(методы `detect` и `collect`) плюс строка в списке `DRIVERS`. Ни опрос, ни веб,
ни хранилище при этом не трогаются.

## Развёртывание и туннели

Пошаговое развёртывание сервиса и постоянных туннелей до объектов (autossh +
systemd, переиспользуемый шаблон на любой объект) — в [deploy/README.md](deploy/README.md).
Коротко: и device-monitor, и туннели живут на одной машине с дашбордом; на
серверах объектов ставить ничего не нужно, туда только идёт SSH.

## Объекты без прямого маршрута (SOCKS-прокси)

Проверка идёт с машины, где запущен сервис, поэтому объект, до которого у неё
нет ни маршрута, ни VPN, показывался бы вечно offline. Для такого объекта у
точки задаётся **SOCKS-прокси** (поле «SOCKS-прокси точки» в настройках точки,
формат `socks5://127.0.0.1:1080`) — и все устройства этой точки проверяются
через него. Прямые точки при этом работают как прежде.

Прокси-узлом служит постоянный SSH-туннель до сети объекта:

```bash
ssh -D 127.0.0.1:1080 -N объект    # или autossh + systemd для постоянки
```

Проверка доступности через прокси не требует зависимостей (свой SOCKS5 CONNECT).
Сбор сведений от железа через прокси пока не идёт (инспекция по HTTP, а он SOCKS
не умеет) — у проксированных точек работает доступность, сведения снимаются
только с точек с прямым доступом.

**Туннель — единая точка отказа, и это учтено.** Если он ляжет, все устройства
точки станут недоступны разом. Сервис отличает «прокси не отвечает» от «порт
устройства закрыт» и показывает у точки состояние **«нет связи с туннелем
объекта»** вместо мнимой массовой гибели устройств. Задержка (`latency`) у
проксированных точек включает время туннеля, а не только сети объекта.

## Если устройства не в маршрутизируемой сети

Когда площадка доступна только через SSH-хост, а не напрямую, поднимите на нём
SOCKS-туннель и ходите через него. Сервис проверяет TCP напрямую и прокси не
использует — в таком случае разворачивайте его на самой площадке.
