# VPN на хосте: WireGuard-туннели

Туннели поднимаются на машине, где крутится Device Monitor, и держатся через
штатные юниты `wg-quick@<имя>` (автозапуск при загрузке, перезапуск при сбое).
Монитор ходит в сети туннелей напрямую через маршруты хоста, поэтому менять его
конфиг не нужно.

## Установка

Конфиги кладём в каталог **вне репозитория** (права 600, владелец вы):

```bash
mkdir -p ~/vpn && chmod 700 ~/vpn
# ~/vpn/wg0.conf, ~/vpn/wg1.conf, ~/vpn/emp24.conf
sudo deploy/vpn/install.sh ~/vpn wg0 wg1 emp24
```

Скрипт перед установкой проверяет:
- нет ли `0.0.0.0/0` в `AllowedIPs` (иначе весь трафик уйдёт в VPN);
- не пересекаются ли `AllowedIPs` выбранных туннелей (`check_overlap.py`).

Если проверка нашла пересечение, установка остановится и ничего не изменит.

## Что делает установка

1. Копирует каждый конфиг в `/etc/wireguard/<имя>.conf` с правами 600.
   Строка `DNS` сохраняется: если у основного интерфейса DNS не задан, через
   туннель с DNS идут имена, и без неё сайты по имени перестают открываться.
2. `systemctl enable --now wg-quick@<имя>` для каждого туннеля.
3. Выводит `wg show`.

## Что проверить после установки

- `wg show` — у каждого туннеля есть `latest handshake`.
- `ip route` — маршруты подсетей ведут в свои `wgN`.
- ТЦ Ала-Арча (`10.30.205.0/24`) доступна через wg0.

## Известные ограничения

- **kk ставится изолированно, не через install.sh.** Его `AllowedIPs`
  (`172.30.11.0/24`, `192.168.158.0/24`) совпадают с wg0, но за ними другие
  сети. См. раздел ниже.
- **openconnect не настроен:** нет адреса шлюза и учётки. Добавим отдельно.
- **Ключи, которые были в переписке, считаем скомпрометированными.** Перевыпустите
  их на серверах и замените файлы в `~/vpn` до установки.

## Объект с теми же подсетями, что у другого туннеля (kk)

Когда два туннеля заявляют одни и те же подсети, а за ними разные объекты,
обычная установка невозможна: маршрут в main один, и трафик уйдёт либо в
одну сеть, либо в другую. Такой туннель ставится изолированно:

```bash
sudo deploy/vpn/install-isolated.sh ~/vpn kk 1050 1082
#                                   каталог имя таблица порт SOCKS
```

- маршруты туннеля пишутся в отдельную таблицу (`Table = 1050`), и main с wg0
  не меняются;
- в эту таблицу смотрит только системный пользователь `dm-kk`, от которого
  работает `microsocks` на `127.0.0.1:1082` (юнит `device-socks-kk`);
- в панели у точки объекта указывается прокси `socks5://127.0.0.1:1082`.
  Дальше всё работает как у точек за `ssh -D`: проверка доступности и кнопка
  «Открыть» через профиль браузера. Сбор сведений с железа через прокси не идёт.
  Отличие: «нет связи с туннелем» панель покажет, только если упал сам прокси.
  Если упал WireGuard, а прокси жив, устройства точки будут просто down.

Сразу после таблицы для `dm-kk` стоит правило `unreachable`. Если туннель
упадёт, без этого правила трафик прокси ушёл бы в main, то есть в wg0, и монитор
показывал бы живыми устройства **чужого** объекта с теми же адресами.

Проверка:

```bash
ip route get 172.30.11.1 uid $(id -u dm-kk)   # → dev kk
ip route get 172.30.11.1                      # → dev wg0 (не изменилось)
systemctl status device-socks-kk
```
