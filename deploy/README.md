# Развёртывание Device Monitor и туннелей до объектов

## Топология

Device Monitor и все туннели крутятся на **одной** машине — там, где вы смотрите
дашборд. На серверах объектов **ничего ставить не нужно**, туда только идёт SSH.

```
ваша машина                                  сервер объекта      устройства
┌────────────────────────────┐              (напр. Балыкчи)     объекта
│ device-monitor (docker)     │                                 ┌─────────┐
│      │ проверка через        │  ssh -D 1081   ┌──────────┐    │ камеры  │
│      ▼                       │ ──────────────►│ SSH-доступ│───►│ роутер  │
│ autossh → SOCKS :1081 ───────┼────────────────│  сервера  │    │ и т.д.  │
│ (systemd, постоянный)        │                └──────────┘    └─────────┘
└────────────────────────────┘
```

Объекты с прямым маршрутом (VPN/локальная сеть) туннеля не требуют — у их точки
поле прокси оставляется пустым, проверка идёт напрямую.

## 1. Сам сервис

```bash
git clone <этот репозиторий> device-monitor && cd device-monitor
cp data/devices.example.json data/devices.json   # или пустой старт
echo "DM_PASSWORD=<сгенерируйте>" > .env
docker compose up -d
```

Панель — http://127.0.0.1:8890.

## 2. Туннель до объекта без прямого маршрута

Нужен только для объектов, до которых у этой машины нет сетевого пути.
Одной командой:

```bash
sudo apt install autossh
sudo ./deploy/setup-tunnel.sh balykchy balykchy 1081
#                             имя      ssh-target порт
```

Скрипт проверит SSH-доступ, поставит systemd-юнит и conf, включит автозапуск и
дождётся, пока порт забиндится. Затем в панели у точки этого объекта впишите в
поле «SOCKS-прокси точки» `socks5://127.0.0.1:1081` — и её устройства начнут
проверяться через туннель.

Если предпочитаете руками — см. шаблоны `device-tunnel@.service` и
`tunnels.example/`, скрипт делает ровно то же.

## Новый объект = одна команда

```bash
sudo ./deploy/setup-tunnel.sh <имя> <ssh-target> <порт>   # порт уникальный
```

Один шаблон юнита обслуживает сколько угодно объектов; порт у каждого свой.

## Кнопка «Открыть» для точек за прокси

У точки с прямым доступом «Открыть» в дашборде открывает веб-интерфейс обычной
вкладкой. У точки за SOCKS-туннелем обычная вкладка до устройства не достучится,
поэтому «Открыть» ведёт через локальный лаунчер, который поднимает **отдельный
профиль браузера этой точки** с её прокси — и морда камеры (включая видео)
работает как при прямом доступе, без ручной настройки `--proxy-server`.

Работает **на машине с дашбордом** (профили браузера локальны). Разовая установка
обработчика:

```bash
./deploy/install-open-handler.sh
```

Регистрирует ссылки `devmon://` на лаунчер `deploy/device-open`. После этого
кнопка «Открыть» у проксированных точек просто работает — для всех текущих и
будущих объектов, профиль и прокси берутся из данных точки, доп. кода на объект
не нужно. Профили лежат в `~/device-monitor-profiles/<точка>/` — по одному на
объект, чтобы сессии камер разных объектов не мешались.

**Поддерживаются Chrome/Chromium и Firefox.** Лаунчер выбирает, что найдёт в
системе (переопределяется через `DEVICE_OPEN_BROWSER`). Разница в том, как
задаётся прокси: Chrome берёт его флагом `--proxy-server`, у Firefox такого
флага нет — ему прокси пишется в `user.js` профиля, который перечитывается при
каждом запуске, поэтому смена порта туннеля подхватывается сама.

Два момента, на которых это ломалось:

- **Каталог профилей не скрытый намеренно.** Firefox из snap не видит
  dot-каталоги в `$HOME` (интерфейс `home` их не отдаёт), и профиль в
  `~/.config/...` молча не открывался бы. Внутри snap у Firefox вдобавок
  подменён `$HOME` на `~/snap/firefox/common`, поэтому путь передаётся
  абсолютным.
- **`--no-remote` обязателен для Firefox.** Без него ссылка уедет в уже
  открытое окно обычного Firefox — мимо профиля с прокси, и камера не
  откроется, хотя туннель исправен.

Прокси из ссылки `devmon://` принимается **только локальный**
(`socks5://127.0.0.1:порт`). Ссылку такого вида может подсунуть любая открытая
в браузере страница, и без этой проверки чужой сайт увёл бы весь трафик
профиля через свой прокси.

## Если туннель ляжет

Панель покажет у точки «нет связи с туннелем объекта» — это отличается от
«устройства не отвечают». autossh переподнимет соединение сам; если не выходит,
смотрите `journalctl -u device-tunnel@<имя>`.
